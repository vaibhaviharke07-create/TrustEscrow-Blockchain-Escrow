# ALG-BC-02 — BLOCKCHAIN ESCROW SYSTEM

## Problem

Unknown buyers and sellers need a trusted way to transact without relying on a centralized intermediary.

Build a decentralized blockchain escrow platform that allows a buyer to lock funds in a smart contract, allows a seller to provide delivery status, allows the buyer to release funds after successful delivery, and supports deadline-based refunds and a basic dispute flow.

# PRIMARY GOAL

The final application must demonstrate this complete end-to-end flow:

1. Buyer connects MetaMask.
2. Buyer selects an Ethereum-compatible testnet.
3. Buyer creates an escrow.
4. Buyer enters seller wallet address.
5. Buyer enters payment amount.
6. Buyer sets a deadline.
7. Smart contract creates the escrow.
8. Buyer deposits/locks test ETH into the smart contract.
9. Funds remain locked inside the smart contract.
10. Seller connects their wallet.
11. Seller can see the escrow assigned to them.
12. Seller marks the order as delivered.
13. Buyer sees that the seller marked it delivered.
14. Buyer releases the funds.
15. Smart contract transfers funds to seller.
16. Transaction is recorded.
17. Reputation/statistics are updated.
18. If the deadline expires before delivery, the buyer can request a refund.
19. If a dispute occurs, either participant can raise a dispute.
20. The dispute enters a dispute state and prevents normal release/refund until resolved.
21. The application clearly shows all blockchain transactions and escrow state transitions.

Do NOT create a fake demo that merely changes values in the frontend.

The critical escrow actions must interact with the deployed Solidity smart contract.

# SMART CONTRACT FUNCTIONS

Implement appropriate functions such as:

### createEscrow

Creates an escrow record.

Inputs should include:

* seller address
* deadline
* optional milestone information if supported

Do not allow invalid seller addresses.

Do not allow buyer == seller.

Do not allow deadlines in the past.

Do not allow zero-value escrow.

---

### deposit

Allows the buyer to deposit/lock funds into the escrow.

The deposited amount must be held by the smart contract.

The contract must emit an event.

---

### markDelivered

Only the seller can call this.

It changes the escrow state to delivered.

Only valid escrow states may transition to delivered.

---

### release

Only the buyer can release funds after the seller marks the escrow delivered.

Transfer the locked funds from the contract to the seller.

Prevent double release.

Update the escrow state.

Emit an event.

---

### refund

Allow the buyer to receive a refund after the deadline has passed if the escrow has not been successfully completed.

Do not allow refund after funds have already been released.

Do not allow unauthorized users to trigger a refund.

---

### raiseDispute

Allow buyer or seller to raise a dispute where appropriate.

Once disputed:

* normal release should be blocked
* normal refund should be blocked

until the dispute is resolved.

---

### resolveDispute

For the MVP, implement a simple trusted-resolution mechanism.

The contract may have an admin/arbitrator address.

The arbitrator can resolve the dispute by choosing:

* refund buyer
* release funds to seller

Clearly explain in the UI that this is an MVP arbitration mechanism and is NOT fully decentralized arbitration.
